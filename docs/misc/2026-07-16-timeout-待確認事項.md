# Timeout 因應機制 — 待確認事項（銀行 / 前端）

> 彙整自《樹配券 2.0 PRD》第九章「網路層 Timeout 因應原則」，供 email 提供給發卡主機（銀行）與前端團隊，請雙方就各自負責的部分提供技術面看法。

## 背景

我們盤點了系統中所有同步跨系統呼叫可能因網路層因素 timeout 的情境（例如呼叫方等待回應期間，因網路而非對方明確拒絕導致無回應），多數情境已有明確的因應原則，但以下項目仍需要銀行、前端從各自技術端確認可行性，才能完成最終定案。

---

## 給銀行（發卡主機）的待確認事項

### 1. `create_order` 與神坊之間的連線層 timeout（對應 PRD §9.3，供確認現行設計是否可行）

**情境**：發卡主機呼叫 `create_order` 後，若因網路因素在 15 秒同步窗內未收到神坊回應（但神坊實際上可能已完成清算並回傳折抵結果，只是回應在傳輸過程中遺失），目前尚未有正式的重試/核對 SOP。

**目前設計方向（2026-07-22 定案）**：貴行端**不需**重送同一 `order_id`，改為連線層 timeout 後非同步呼叫 `bank_get_order` 查詢該筆訂單實際結果（`processing`/`error` 等），依查詢結果更新貴行內部的折抵／入帳資料，使雙方狀態一致；若查詢結果顯示此筆折抵不應存在（例如該筆刷卡已被貴行判定應取消），可透過現有的 `batch_finalize_orders`（action=`cancel`）取消／回沖已入帳的折抵。

**請協助確認：**
1. 上述「非同步查詢 `bank_get_order` 後更新貴行本地折抵資料」的做法，貴行端是否具備技術可行性？查詢的時機與頻率上是否有建議做法（例如固定延遲後查一次、或排入既有對帳排程）？
2. 透過 `batch_finalize_orders`（action=`cancel`）取消／回沖已入帳折抵的既有流程，是否足以涵蓋上述取消情境？或有其他既定流程？

### 2. `batch_finalize_orders` 等待回應 ack 的連線層 timeout（對應 PRD §9.4，供確認現行設計是否可行）

**目前設計方向**：發卡主機若在等待 `batch_finalize_orders` 的 `200 OK` 回應時遇到本地連線 timeout，可直接安心重送同一 `request_id`；若重送收到 `400 BATCH_REQUEST_ALREADY_EXISTS`，即代表該批次已受理，不需額外查詢確認。

**請協助確認：** 貴行端的重試邏輯是否可依此設計實作？是否有其他考量或限制？

## 給前端團隊的待確認事項

### 3. `activate_member` / `deactivate_member` 逾時後的重試（對應 PRD §9.5，供確認現行設計是否可行）

> ⚠️ 2026-07-22 起，兩支 API 的成敗判定基準不再對稱，請分別參考：

**`activate_member`（維持點數系統成功才算完成）：**
- 因為授權操作本身具冪等性（重複呼叫不會產生副作用，已為 `TRUE` 時重複呼叫不重複寫入紀錄），前端在請求逾時未收到回應時，可直接重新呼叫同一支 API，不需要額外的查詢確認機制
- 點數系統失敗（含 timeout）：整筆失敗、樹配券狀態不變，前端可安全重試
- 點數系統成功、樹配券本地端寫入失敗：屬非預期錯誤，由樹配券端 5xx + Sentry alert 走人工介入，不需要前端額外處理

**`deactivate_member`（改為樹配券本地寫入成功即完成）：**
- 樹配券收到請求並完成本地寫入即回覆成功；點數系統呼叫（`member_unauthorize`）改為 best-effort，其失敗不影響本次 API 回應，改由樹配券端觸發告警走人工補正，前端不需要額外處理
- 前端收到成功回應即可視為完成；逾時未收到回應時的重試方式與 `activate_member` 相同（本操作亦具冪等性）

**請協助確認：** 上述重試方式在前端 UX 上是否可行？是否需要額外的 loading 狀態或防連點設計？

### 4. `update_member_selected_brands` 逾時後的重送建議（對應 PRD §9.6）

**背景**：我們的理解是，後端本身不限制品牌更換次數，但前端會自行限制「每 N 天僅能更改一次」。若請求因逾時未收到回應，前端若直接盲目重送，可能造成：
1. 後端多寫入一筆變更紀錄（`change_selected_brands` 事件）
2. 若前端判斷「本次額度是否已用掉」的依據恰好是這筆變更紀錄或 `last_brand_selection_changed_at`，重複寫入可能讓前端誤判使用者已變更過，錯誤地擋下使用者原本合法的下一次操作

**目前建議做法**：前端在逾時未收到回應時，先重新呼叫 `get_member_settings`（或 `get_member_settings_change_logs`）確認該筆變更是否已生效，確認未生效才重送。

**請協助確認：**
1. 我們對「每 N 天限一次」判斷邏輯的理解是否正確？實際的 N 值與判斷依據為何？
2. 上述「先查證再重送」的建議是否可行？是否有更適合前端現有架構的做法？
