## 一、專案背景

原規劃方案「點數 + 金流整合支付（點加金）」因法規限制暫緩，本次改以「券加金」模式推動，即樹配券 2.0。

核心機制：用戶以點數兌換由神坊發行的「消費券（coupon）」，並於刷卡時即時折抵消費金額，在定性上趨近於消費代金，與一般禮票券有所區別。

## 二、名詞定義

### Rotation（輪播檔期）

#### 概念

定義活動起訖時間（`start_time` ～ `end_time`）、本檔期品牌選擇上限（`max_selectable_auto_brand_count`）、本檔期每會員合計可用點數上限（`max_points_per_member`）與前端顯示參數（`description`）。所有 campaign、用戶品牌選擇與 coupon 均以 rotation 為時間邊界。

#### 規則

1. 依 `start_time <= now() <= end_time` 判斷是否為 active rotation（end_time 含邊界）
2. 系統同一時間只應有一個 active rotation；建立 rotation 時須檢查 `next.start_time > prev.end_time`（嚴格大於），避免前後緊接的 rotation 在交界瞬間同時判定為 active
3. 用戶的品牌選擇（`member_selected_brands`）與所選當下的 rotation 綁定，換檔後透過 lazy cleanup 自動失效
4. 不屬於當前 active rotation 的 campaign，一律視為非 active，無法觸發產券或兌換
5. `max_points_per_member` 為 **rotation 屬性**：同一用戶於此 rotation 內、跨所有品牌與 campaign 合計可用的點數上限；計數為同一 `member_id + rotation_id` 下已發行 coupon 的 `coupon_redeem_points` 加總（含全狀態）；`0` 代表無上限

---

### Brand（特店）

#### 概念

合作的品牌通路，亦稱為特店（例：全家、7-11、康是美）。brand 是 campaign 與 coupon 的頂層歸屬，也是用戶選擇自動兌換對象的單位。

#### 規則

1. 每個 brand 必須有唯一的 `treepoint_merchant_provider_key`，作為點數帳務通路識別，DB 不可為 null
2. 一個 brand 可跨多個 rotation 參與活動，每個 rotation 下可掛載多個 campaign
3. 同一 brand 同一時間只允許一個 `type = auto` 的 active campaign；`type = manual` 無此限制，可同時有多個 active

---

### Campaign（兌換活動）

#### 概念

定義特定 brand 在特定 rotation 內的產券規則，包含兌換門檻（`coupon_min_order_amount`）、所需點數（`coupon_redeem_points`）、折抵金額（`coupon_discount_amount`）與單筆上限（`max_redemptions_per_order`）。campaign 是 coupon 的發行依據。

> 檔期層級的兌換上限已改由 rotation 屬性 `max_points_per_member`（計點數）承接；原 campaign 屬性 `max_redemption_per_rotation`（計張數）已於 2026-07-08 廢除。

#### 規則

1. campaign 本身不直接關聯 rotation；透過 `brand_rotation_campaigns` 中間表掛載，支援同一 campaign 沿用於多個 rotation
2. 未掛載任何 rotation 的 campaign 不生效，但可提前建立備料；active 判斷為：`brand_rotation_campaigns` 中是否存在對應當前 active rotation 的記錄
3. `type` 分為 `auto`（刷卡時自動觸發清算）與 `manual`（由用戶主動發起換券），一經建立不得更改
4. 同一 brand 同一時間只允許一個 `type = auto` 的 active campaign；`type = manual` 無此限制，可同時有多個 active
5. 兌換規則欄位 `coupon_min_order_amount`、`coupon_redeem_points`、`coupon_discount_amount` 皆須大於 0；`max_redemptions_per_order` 可為 `0`（代表無上限）
6. `member_selected_brands`（品牌預選清單）、lazy cleanup 與 `create_order` 清算機制僅服務 `type = auto` campaign；`type = manual` 的兌換由用戶主動發起，不受品牌預選清單限制，也不透過 `create_order` 觸發。`manual` 型目前僅有資料定義與 `get_current_rotation` 呈現規則，尚無對應的兌換執行 API/流程（詳見 `api_list.md` 待新增項目）

---

### Coupon（折抵券）

#### 概念

基於 campaign 產出、歸屬於特定用戶的折抵券 instance。每張 coupon 在建立時快照 campaign 的兌換規則與所在 rotation，確保後續統計與清算不受 campaign 事後變動影響。

#### 規則

1. coupon 建立時快照 `coupon_min_order_amount`、`coupon_redeem_points`、`coupon_discount_amount` 與 `rotation_id`，寫入後為唯讀
2. `expired_at` 於發券時一次計算寫死（`created_at 所在 UTC+8 日期 + coupon_valid_days` 之 `23:59:59.999`），不隨後續異動更新
3. 狀態機：`available → consumed → settled`；取消時 `consumed → available`（未到期）或 `consumed → expired`（已到期）
4. 狀態為 `consumed` 的 coupon 不可納入下一筆交易的折抵計算

---

### Coupon Wallet（券夾）

#### 概念

用戶所有 coupon 的查詢視角，不是獨立資料表，而是對 `coupons` 表依 `member_id`、`brand_id`、`status` 組合查詢的投影。

#### 規則

1. 前端券夾首頁以品牌摘要呈現（`get_coupon_wallet`），點入品牌後才展示券列表（`get_coupons`）
2. 摘要顯示的 `available_coupon_count` 聚合 `status IN (available, consumed)` 的券張數（尚可用或使用中皆計入）

---

### Point Balance（點數餘額）

#### 概念

用戶目前可用於兌換 coupon 的點數餘額，屬外部點數系統（TreePoint）管理，本系統不另設點數帳務表。

#### 規則

1. 點數在 `create_order` 時即時扣除，本系統不保存點數餘額
2. 訂單取消後點數不退還；券未到期則回 `available`，已到期則回 `expired`
3. 扣點時系統依訂單所屬 brand 的 `treepoint_merchant_provider_key` 作為通路識別

## 三、Coupon 狀態機

| 狀態 | 說明 | 可觸發的轉換 |
| --- | --- | --- |
| `available` | 可使用，存在於用戶券夾 | `consumed`（成立訂單）<br>`expired`（到期） |
| `consumed` | 交易授權中，等待商戶請款 | `settled`（請款完成）<br>`available`（取消且未到期）<br>`expired`（取消時已到期） |
| `settled` | 核銷完成，神坊代償完畢 | 終態 |
| `expired` | 超過有效期限自動過期 | 終態 |

> 注意：`consumed` 狀態的 `coupon` 在後續新訂單計算時不可再被使用，僅 `available` 的 `coupon` 可納入折抵計算。

## 四、Brand / Campaign 規則欄位

### 4.1 Brand 欄位

| 欄位 | 類型 | 說明 |
| --- | --- | --- |
| `brand_id` | String | `brand` 主鍵（ULID），用於識別品牌主資料。 |
| `brand_name` | String | 品牌名稱，供前台顯示與後台維護使用。 |
| `brand_logo` | String | 品牌 Logo 資源位置或識別值，供前台品牌展示使用。 |
| `brand_category` | String | 品牌分類，用於品牌分組、顯示或營運管理。 |
| `treepoint_merchant_provider_key` | String | 該 `brand` 對應的 TreePoint 用點通路識別。執行 `create_order` 扣點時，系統需依 `brand` 讀取此欄位並帶入點數帳務流程，以區分點數是用於全家換券、7-11 換券等不同品牌場景。此欄位為品牌主資料必填，DB 不可為 `null`。 |
| `created_at` | DateTime | `brand` 建立時間（UTC+8 ISO 8601）。 |
| `updated_at` | DateTime | `brand` 最後更新時間（UTC+8 ISO 8601）。 |

### 4.2 Campaign 欄位

| 欄位 | 類型 | 說明 |
| --- | --- | --- |
| `campaign_id` | String | `campaign` 主鍵（ULID）。 |
| `brand_id` | String | 對應 `brand` 主鍵（ULID），表示該 `campaign` 隸屬哪一個品牌。 |
| `type` | String | `auto`（系統自動兌換）\| `manual`（用戶手動兌換）。`auto` 型在刷卡時自動觸發清算；`manual` 型由用戶主動發起換券。**一經建立不得更改。** |
| `campaign_name` | String | `campaign` 名稱，供後台辨識與營運維護使用。 |
| `coupon_min_order_amount` | Integer | 【門檻】每消費滿 N 元，可對應使用一張 `coupon` |
| `coupon_redeem_points` | Integer | 兌換一張 `coupon` 所需點數 |
| `coupon_discount_amount` | Integer | 一張 `coupon` 可折抵的金額（元） |
| `max_redemptions_per_order` | Integer | 單筆交易中，當前 active campaign 最多可使用幾張券；`0` 代表無上限 |
| `created_at` | DateTime | `campaign` 建立時間（UTC+8 ISO 8601）。 |
| `updated_at` | DateTime | `campaign` 最後更新時間（UTC+8 ISO 8601）。 |

`campaign` 的 active 狀態由 `brand_rotation_campaigns` 是否存在對應當前 active rotation 的記錄推導，`campaign` 本身不另設 `start_at` / `end_at`，也不直接持有 `rotation_id`。每一 `brand` 底下同一時間只允許一個 `type = auto` 的 active campaign；`type = manual` 無此限制。用戶需事先同意「刷卡時自動以點數兌換」，系統才會在刷卡時觸發清算。

> **現況提示：** `type = manual` 的 campaign 欄位定義與上述規則已確立，但目前僅止於資料模型與 `get_current_rotation` 的呈現（供前端「手動換券頁面」顯示規則），尚無對應的用戶主動兌換 API 或流程，屬於待補齊項目。

### 4.3 全域參數（system_configs）

| 欄位 | 類型 | 說明 |
| --- | --- | --- |
| `coupon_valid_days` | Integer | 全域 coupon 有效天數設定，不屬於 `campaign` 欄位。發券時需以 `issued_at` 所在 UTC+8 日期加上此天數後，取當日 `23:59:59.999` 作為 `coupon.expired_at`；`0` 代表當日到期（即 `issued_at` 當日 `23:59:59.999`）。 |
> 注意：`brand_selection_limit` 已移至 `rotations` 表，由各檔期自行定義，詳見第十章「Rotation 輪播檔期」。

### 4.4 Rotation 欄位

| 欄位 | 類型 | 說明 |
| --- | --- | --- |
| `id` | String | 輪播檔期主鍵（ULID） |
| `name` | String | 檔期名稱 |
| `start_time` | DateTime | 檔期開始時間（UTC+8 ISO 8601） |
| `end_time` | DateTime | 檔期結束時間（UTC+8 ISO 8601） |
| `max_selectable_auto_brand_count` | Integer | 本檔期用戶最多可選（具備 active `auto` campaign 之）品牌數量 |
| `max_points_per_member` | Integer | 同一用戶於此 rotation 內、跨所有品牌與 campaign 合計可用的點數上限；`0` 代表無上限 |
| `description` | String | 前端顯示用說明參數，JSON 字串格式：`{"order_amount": N, "point_amount": N}`，由前端自行 parse 呈現 |

> 注意：`description` 目前不影響實際清算，清算依各品牌 `campaign` 的 `coupon_min_order_amount`、`coupon_redeem_points` 規則執行。

> 注意：`max_selectable_auto_brand_count` 僅計入具備 active `auto` campaign 之品牌；`manual` campaign 目前無對應的品牌選擇／兌換執行機制（`member_selected_brands`、lazy cleanup、`create_order` 清算皆僅服務 `auto`），此欄位現階段可視為專屬 auto 使用。未來若需將 manual 品牌納入選擇上限，須另行設計（可能修改或新增 DB 欄位），非本欄位現有語意涵蓋範圍。

## 五、清算邏輯（create_order）

### 5.1 前置條件與成敗判定

**前置驗證（不通過即不建立訂單）：**

- 會員必須已啟用（`members.is_activated = TRUE`），否則回 `MEMBER_NOT_ACTIVATED`
- `order_id` 全系統唯一（含 `error` 訂單皆佔用），重複回 `ORDER_ALREADY_EXISTS`
- `brand_id` 不做前置存在性檢查；不存在或無效者於清算階段自然導致折抵為 0

**成敗判定（單一條件）：**

- 清算分兩段執行：**既有券段**（使用既有 `available` 舊券，必成段）與**新券段**（扣點、即時發新券，best effort）
- `discount_amount > 0` → 建單成功，訂單進入 `processing`，等待 `batch_finalize_orders`
- `discount_amount = 0` → 訂單標記 `error` 並記錄 `error_type`（`NO_ACTIVE_CAMPAIGN`、`AUTO_REDEEM_NOT_ENABLED`、`NO_AVAILABLE_COUPON_AND_POINT`、`ORDER_AMOUNT_BELOW_MIN_AMOUNT`、`MEMBER_EXCEED_PER_ROTATION_POINT_LIMIT`、`TREELIFE_ERROR`），API 回傳對應失敗碼

> 注意：即使該 brand 當前無 active campaign、會員已暫停自動兌換（`members.auto_redeem_enabled = FALSE`，會員層級開關）、或該品牌未入選（見下），只要有符合門檻的 `available` 舊券，仍照常執行既有券段清算；上述條件僅使新券段被跳過，不視為錯誤。

**品牌入選為新券段前置條件（2026-07-13 定案）**：`member_selected_brands` 須存在 `member_id + brand_id + rotation_id`（當前 active rotation）三者完全符合之記錄，才進入新券清算；未入選僅跳過新券段，未入選且無可用舊券時歸入 `NO_ACTIVE_CAMPAIGN`。

### 5.2 計算步驟

**既有券段（必成段，清算完成即 commit）：**

1. 取出用戶在此 `brand` 下所有 `available` 且未過期的 coupons，依 `expired_at ASC → created_at ASC → coupon_id ASC` 排序（FIFO）
2. 逐張檢查：剩餘消費額 ≥ 該券 `coupon_min_order_amount` 才使用，否則跳過該券繼續檢查下一張；每張券整張使用，不做部分用券
3. 屬於當前 active campaign 的舊券，受 `max_redemptions_per_order` 限制（`0` 代表無上限），達上限後同 campaign 舊券全部跳過；歷史 campaign 舊券不受此限
4. 所有被使用的既有券狀態改為 `consumed`

**新券段（best effort，失敗不推翻既有券段）：**

1. 剩餘消費額 = `order_amount` − Σ（已使用既有券的 `coupon_min_order_amount`）
2. 若無 active campaign、會員 `auto_redeem_enabled = FALSE`、或該品牌未入選（`member_selected_brands` 無 `member_id + brand_id + rotation_id` 完全符合之記錄），跳過新券段
3. 計算 per-rotation 點數 quota：`max_points_per_member = 0` 視為無上限；否則剩餘點數預算 = `max_points_per_member` − Σ（同一 `member_id + rotation_id` 下已發行券的 `coupon_redeem_points`，跨品牌、含全狀態）；預算 ≤ 0 則跳過新券段
4. **依序發券**：自第一張起逐張檢查以下條件是否同時成立——(a) 剩餘消費額 ≥ `coupon_min_order_amount`；(b) 剩餘點數 ≥ `coupon_redeem_points`；(c) 剩餘 rotation 點數預算 ≥ `coupon_redeem_points`（無上限則略過）。成立即計入一張並各自扣減，重複至任一條件不成立為止
5. 呼叫 treelife-api 扣點（依 `brand.treepoint_merchant_provider_key` 作帳務歸屬；cub_points 優先分配給先發行的券），成功後即時發出新券（狀態 `consumed`），`expired_at = (issued_at 所在 UTC+8 日期 + coupon_valid_days) 的 23:59:59.999`

> 注意：新券段**不檢查** `max_redemptions_per_order`；該上限僅約束既有券段中 active-campaign 舊券的張數，能進入新券段即代表 per-order 尚未占滿。

`discount_amount` = Σ（本次所有 `consumed` coupon 的 `coupon_discount_amount`，含既有券段與新券段）。

`create_order` response 回傳 `discount_amount` 與 `coupon_summary`（`new_issued`／`existing` 兩組彙總，各含 `discount_amount`/`tree_points`/`cub_points`；`existing` 列出的點數為該些舊券**原始發行時**的歷史組成，非本次消耗——是否為本次新消耗已由所屬分組區分，無需另外歸零）。發卡主機若需事後重查，應另呼叫 `bank_get_order`；前台端訂單瀏覽改用 `get_member_orders` 摘要列表（前台不提供單筆訂單完整明細查詢，`get_order` 已於 2026-07-08 廢除）。

### 5.3 Transaction 邊界與失敗處理

- 清算採**兩段 DB transaction**：
  - **stage 1（既有券段）**：單一 transaction 內建立 order（狀態 `pending`）、既有券段清算（舊券轉 `consumed`）、建立 order event 後 commit
  - **stage 2（新券段）**：另一 transaction 執行扣點、發新券，完成後將折抵與點數 update 併回同一筆 order
  - 兩段皆須於發卡主機可接受的 **15 秒**同步窗內完成後回覆
- 新券段失敗分兩類，皆不改變成敗判定（僅影響善後）：
  - **點數端失敗**（treelife-api 扣點 fail / timeout）：屬網路層 timeout 因應範疇，詳細機制（cronjob 對帳、退點、未來優化方向）移至第十二章「網路層 Timeout 因應原則」12.2 節
  - **我方失敗**（扣點成功但發券寫入失敗）：孤兒點數，屬 5xx 非預期錯誤，人工事後補券或退點
- `store_name`、`card_last_four_digits`、`transaction_time` 由發卡主機建單時提供，神坊原樣快照保存於訂單資料，僅供後續查詢顯示，不參與任何清算邏輯
- 執行點數扣除時，系統依訂單所屬 `brand` 的 `treepoint_merchant_provider_key` 作為點數帳務通路識別

### 5.4 計算範例

情境設定：

| 項目 | 數值 |
| --- | --- |
| 訂單金額（`order_amount`） | 620 元 |
| 用戶 `point_balance` | 26 點 |
| rotation `max_points_per_member` | 0（無上限） |
| active campaign | 滿 100 折 21：`coupon_min_order_amount=100`、`coupon_redeem_points=20`、`coupon_discount_amount=21`、`max_redemptions_per_order=3` |
| `coupon_wallet` 中既有券 | `coupon_01`（歷史 campaign）：`coupon_min_order_amount=400`、`coupon_discount_amount=120`、原始發行時 `redeem_points=100`（`tree_points=15`、`cub_points=85`） |

計算過程：

1. **既有券段**：FIFO 取出 `coupon_01`（唯一 `available` 券），`620 ≥ 400` → 使用，狀態轉 `consumed`：

   ```text
   剩餘消費額 = 620 - 400 = 220
   ```

2. **新券段（依序發券）**：

   ```text
   第 1 張：220 ≥ 100 ✓、26 ≥ 20 ✓ → 發行；剩餘消費額 120、剩餘點數 6
   第 2 張：120 ≥ 100 ✓、但 6 < 20 ✗ → 停止
   ```

3. 呼叫 treelife-api 扣點 20（回傳拆分例：`tree_points=8`、`cub_points=12`），派發 `coupon_02`（`consumed`）。
4. 折抵總額 `120 + 21 = 141 > 0` → 訂單進入 `processing`。

Response 範例：

```json
{
  "discount_amount": 141,
  "coupon_summary": {
    "new_issued": { "discount_amount": 21, "tree_points": 8, "cub_points": 12 },
    "existing": { "discount_amount": 120, "tree_points": 15, "cub_points": 85 }
  }
}
```

### 5.5 帳務流程

1. 用戶授權商戶刷卡 620 元。
2. 神坊扣除用戶點數 20 點。
3. 商戶向銀行請款 620 元。
4. 神坊確認核銷 `coupon_01` + `coupon_02`。
5. 神坊代償 141 元給銀行。
6. 用戶實際應繳卡費：`620 - 141 = 479` 元。

### 5.6 重複請求處理規則

- `create_order` 以 `order_id` 作為唯一訂單識別，且與點數系統的扣點交易為**一對一關係**。
- 同一 `order_id` 已建立後（不論最終為 `processing` 或 `error`，皆佔用 `order_id`），任何再次收到的 `create_order` 請求一律回 `ORDER_ALREADY_EXISTS`，不重做清算。
- 不區分再次收到的請求內容是否與首次一致；即使 `brand_id`、`order_amount` 或其他欄位不同，仍回 `ORDER_ALREADY_EXISTS`。
- 重複建立不得再次扣點、發券、改券狀態或新增事件。
- 首次 `create_order` 成功（`discount_amount > 0`）後，訂單即進入 `processing` 狀態，等待後續 `batch_finalize_orders`。

## 六、訂單生命週期

| 事件 | 觸發方 | Coupon 狀態變化 | 點數 |
| --- | --- | --- | --- |
| `create_order`<br>（刷卡授權後） | 發卡主機 | 既有券 `available` → `consumed`；新券直接以 `consumed` 發行 | 新券段即時扣除 |
| `batch_finalize_orders`<br>（商戶請款完成，action=complete） | 發卡主機 | `consumed` → `settled` | 不異動 |
| `batch_finalize_orders`<br>（商戶取消交易，action=cancel） | 發卡主機 | `consumed` → `available`（未到期）<br>`consumed` → `expired`（已到期） | 不退還 |

> 注意：`create_order` 與 `batch_finalize_orders` 為非同步，兩者之間可能有數天時間差。`consumed` 期間的券不可再被計入下一筆交易的折抵計算。

> 注意：取消交易後，本次交易即時兌換產生的新券（如 `coupon_02`）若在 finalize 當下尚未到期，則回 `available`；若已到期，則回 `expired`。點數不返還。

### 6.1 訂單狀態（`order.status`，五態）

| order.status | 說明 | 進入時機 |
| --- | --- | --- |
| `pending` | 剛建立，涵蓋清算執行中（既有券段 + 新券段），無獨立的「清算中」狀態值 | stage 1 一開始即建立 order |
| `processing` | 清算完成、待終結 | 清算完成且 `discount_amount > 0`，等待 `batch_finalize_orders` |
| `error` | 清算完成、失敗 | 清算完成且 `discount_amount = 0`，記錄 `error_type` |
| `completed` | 已終結 | `batch_finalize_orders` action=`complete` |
| `cancelled` | 已終結（取消） | `batch_finalize_orders` action=`cancel` |

- `processing` 是唯一可執行 `batch_finalize_orders` 終結的狀態。
- `completed`、`cancelled` 為終態，進入後不得再次轉換；`error` 亦不可終結（批次內回 `ORDER_NOT_FOUND`）。
- 可查性：`get_member_orders` 剔除 `error`（且 `pending` 暫態不出現）；admin 端可經 status filter 查得；`bank_get_order` 不分 status 一律全回。

### 6.2 batch_finalize_orders 批次與非同步機制

- `batch_finalize_orders` 採 `multipart/form-data`（訂單資料為 JSON Lines / ndjson 格式）批次接收：發卡主機一次可傳入多筆 `{order_id, action}`（單批次以檔案大小 < 10MB 為上限，不再固定筆數），神坊立即回 `200 OK`（無 body），實際狀態轉換以非同步方式執行。
- 發卡主機自行產生 `request_id` 並帶入請求；重送相同 `request_id` 時，神坊回 `400 BATCH_REQUEST_ALREADY_EXISTS`，不重複建立或執行。
- 發卡主機可透過 `get_finalize_batch_status` 查詢各筆訂單的處理進度。
- 單筆處理失敗（`INVALID_ACTION`、`ORDER_NOT_FOUND`、`ORDER_ALREADY_FINALIZED`）不中斷整批次，失敗原因記錄於該筆的 `error_code`。

### 6.3 重複 finalize 規則

- 同一 `order_id` 已完成最終化後，再次被納入批次時，該筆 item 標記為 `FAILED`，`error_code = ORDER_ALREADY_FINALIZED`。
- 不區分再次收到的是相同結果或不同結果；已 `completed` 後收到 `CANCELLED`，或已 `cancelled` 後收到 `COMPLETED`，皆以 `ORDER_ALREADY_FINALIZED` 記錄失敗。
- 重複 finalize 不得再次改變訂單狀態、券狀態、點數或新增事件。

## 七、資訊流程

### Flow 1：品牌一覽

用戶可瀏覽所有合作品牌及對應的當期自動兌換規則。

需回傳欄位（對應 `get_current_rotation`）：

- `max_selectable_auto_brand_count`
- `max_points_per_member`
- `brand_name`
- `brand_logo`
- `brand_category`
- `brand_active_campaign_details`（`coupon_min_order_amount`、`coupon_redeem_points`、`coupon_discount_amount`、`max_redemptions_per_order`）

### Flow 2：會員啟用

用戶需先同意樹配券平台可使用其點數，作為後續品牌設定與 `create_order` 用點清算的前置條件。啟用操作分為兩個獨立 endpoint：

**同意服務（`activate_member`，原 `member_authorize`）**
- 用戶在 CR 前台首次同意或重新同意樹配券服務
- 神坊呼叫點數系統 API，兩邊皆成功後更新 `members.is_activated = TRUE`，寫入一筆 `member_event_logs`（type=`activate_member`）；API 對外回傳 `status: ACTIVE`
- 冪等：已為 `TRUE` 時重複呼叫不重複寫 log

**解除服務（`deactivate_member`，原 `member_unauthorize`）**
- 用戶在 CR 前台主動解除服務
- 神坊更新 `members.is_activated = FALSE`，寫入一筆 `member_event_logs`（type=`deactivate_member`）；API 對外回傳 `status: INACTIVE`
- 解除後 `available` coupon 保留但不可用於新交易；`consumed` 狀態的 order 繼續走完原流程
- 冪等：已為 `FALSE` 時重複呼叫不重複寫 log

**啟用歷史**
- 完整異動歷史保存於 `member_event_logs`（統一會員事件表，原 `member_activation_logs` 已併入），未來透過後台 API 供客服查詢（第二階段，端點名稱待定）

### Flow 3：選擇品牌

用戶選擇偏好的 `brand` 加入自動兌換清單。

系統需驗證：

- 會員必須已啟用（`members.is_activated = TRUE`）。
- 用戶已選品牌數量：不超過當前 active rotation 的 `max_selectable_auto_brand_count`。
- 所選 `brand` 是否有 active `auto` campaign。

### Flow 4：瀏覽已選品牌

顯示用戶目前的品牌設定狀態，包含服務是否啟用，以及已選擇的品牌 ID 清單。

需回傳欄位：

- `auto_redeem_enabled`
- `last_brand_selection_changed_at`
- `selected_brand_ids`：已選且當前仍具備 active auto campaign 的品牌 id 清單

> 前端如需品牌名稱、logo、campaign 詳情，應另呼叫 `get_current_rotation`；`max_selectable_auto_brand_count` 亦由 `get_current_rotation` 取得。

若用戶處於暫停用券狀態，仍可回傳目前已選且當前有 active `auto` campaign 的品牌 id 清單，但 `auto_redeem_enabled = false`。

`last_brand_selection_changed_at` 代表該用戶品牌選擇狀態最近一次異動時間，僅於首次選牌、更換品牌時更新；`PAUSE` / `RESUME`、lazy cleanup 換檔清空皆不更新此欄位。

### Flow 5：異動紀錄

調閱用戶過往 1 年內（查詢當下 T-366 天，含；資料不清除，僅查詢範圍有上限）的品牌選擇異動紀錄，包含：

- 異動時間
- 異動行為（首次啟用、暫停用券、重啟用券、更換品牌）
- 更換品牌需記錄「更換前的品牌清單」vs「更換後的品牌清單」

底層資料模型採 `member_event_logs`（統一會員事件表，原 `member_brand_change_logs` 已併入）request 粒度事件模型：

- 每次品牌異動或服務狀態切換各寫入**一筆**紀錄
- 選牌相關 `type`：`change_selected_brands` | `system_clear_brands` | `disable_auto_redeem` | `enable_auto_redeem`（同表另有會員啟用事件 `activate_member` / `deactivate_member`，見 Flow 2）
- `data` 欄位（nullable JSON），儲存**快照**（非 diff），可直接作為 API 回傳值：
  - `type = change_selected_brands`（首次選牌與後續換牌）：格式 `{"before_brands": [{"id": "...", "name": "..."}], "after_brands": [{"id": "...", "name": "..."}]}`；首次選牌時 `before_brands = []`
  - `type = system_clear_brands`（lazy cleanup 清空）：`{"before_brands": [被清除品牌快照], "after_brands": []}`；`created_at` 設為舊 rotation 的 `end_time`
  - `type = disable_auto_redeem` / `enable_auto_redeem`（暫停／啟用服務）：`data = null`
- `members.auto_redeem_enabled` 記錄當前狀態；`member_event_logs` 同時保存完整歷程（含 pause/resume）

### Flow 5-1：Rotation 換檔後自動清空已選品牌（Lazy Cleanup）

系統採用「用戶進入時觸發」的 lazy cleanup 機制取代批次清除，不需要額外的 batch job。

規則如下：

- 觸發點：用戶呼叫 `get_member_settings`、`update_member_selected_brands`、`create_order` 等需讀取已選品牌的 API 時自動執行
- 判斷條件：比對 `member_selected_brands.rotation_id` 與當前 active rotation 的 `id`，若不符則代表舊檔期選擇已失效
- 清除動作：
  - 刪除該用戶在 `member_selected_brands` 中的所有舊檔期記錄
  - 在 `member_event_logs` 寫入一筆 `system_clear_brands` 事件：`data = {"before_brands": [被清除品牌快照], "after_brands": []}`，`created_at` 設為舊 rotation 的 `end_time`
- `auto_redeem_enabled` 保留原值不受影響
- 冪等性：若已選品牌已為空，skip，不重複寫入 change log
- `last_brand_selection_changed_at` **不受影響**：lazy cleanup 不更新此欄位（僅首次選牌、更換品牌時更新）

### Flow 6：券夾

券夾採三層瀏覽：品牌摘要（`get_coupon_wallet`）→ 品牌券列表（`get_coupons`）→ 單張券詳情（`get_coupon_detail`）。

**品牌摘要（`get_coupon_wallet`）**：回傳用戶所有曾經產生 coupon 發行紀錄的品牌卡片列表（不限時間），不限於當前 rotation 或當前已選品牌；每筆含 `id`、`name`、`logo`、`available_coupon_count`（聚合 `available` + `consumed` 張數，尚可用或使用中皆計入）。

**券列表（`get_coupons`）**：支援 `brand_id` 與 `status[]`（可複選）篩選；前端以三個獨立列表呈現：**待折抵**（`available` + `consumed`）、**已折抵**（`settled`）、**已過期**（`expired`），各自獨立查詢與分頁，不合併呈現（`settled`／`expired` 排序欄位不同，不應合併查詢）。回傳為列表精簡欄位：

- `id`
- `status`
- `campaign_name`
- `min_order_amount`
- `discount_amount`
- `expired_at`

**券詳情（`get_coupon_detail`）**：於列表欄位之外另含 `brand {id, name, logo}`、`campaign {id, name, type}`、`redeem_points`（兌換時花費點數合計快照）、`tree_points`/`cub_points`（該點數合計拆分為小樹點生活／信用卡兩種組成，同快照）、`discount_rate`、`max_redemptions_per_order`、`created_at`（即有效期間起始時間，與 `expired_at` 構成完整起迄，精度一致為毫秒）。

### Flow 7：刷卡

> 本節僅涵蓋 `type = auto` 的自動兌換流程；`type = manual` 的用戶主動兌換流程尚未定義，詳見 `api_list.md` 待新增項目。

子流程 7a：`create_order`（信用卡授權後同步執行）

- 由發卡主機呼叫，帶入 `order_id`、`member_id`、`brand_id`、`order_amount`、`card_last_four_digits`、`store_name`（刷卡門市名稱）與 `transaction_time`（刷卡交易時間，呈現用）。
- 神坊執行第五章清算邏輯，回傳 `discount_amount` 與 `coupon_summary`（`new_issued`／`existing` 兩組彙總）。
- 發卡主機端若需查詢訂單狀態與折抵金額，另以同一 `order_id` 呼叫 `bank_get_order`（前台 `get_order` 已於 2026-07-08 廢除，前台改用 `get_member_orders` 摘要列表）。
- 若同一 `order_id` 再次建立，一律回 `ORDER_ALREADY_EXISTS`，不重做清算。

訂單底層資料模型包含：

- `order_logs`：保存 `CREATED`、`COMPLETED`、`CANCELLED` 等訂單歷程事件
- `order_coupon_logs`：保存本次訂單實際使用的券明細快照
- `treelife_use_point_log`：保存新券的點數分配（每張券的 `used_tree_points` / `used_cub_points`，cub 優先填滿）

> `card_last_four_digits`、`store_name`、`transaction_time` 僅作為訂單顯示資訊快照保存，不參與任何品牌識別、點數清算或折抵計算邏輯。

子流程 7b：`batch_finalize_orders`（商戶請款或取消交易後批次非同步執行）

- 發卡主機以批次方式傳入 `request_id` 與多筆 `{order_id, action}`，神坊立即回 `200 OK`（無 body）。
- 請款成功（`action = complete`）：`coupon` 狀態 `consumed` → `settled`，神坊代償，訂單 `processing` → `completed`。
- 取消交易（`action = cancel`）：`coupon` 狀態依是否已到期轉為 `available` 或 `expired`，點數不退還，訂單 `processing` → `cancelled`。
- 若該 `order_id` 已完成最終化，該筆記錄失敗（`error_code = ORDER_ALREADY_FINALIZED`），不影響同批次其他筆。
- 發卡主機可透過 `get_finalize_batch_status` 輪詢批次執行進度。

## 九、商務規則彙整（環境參數）

| 規則 | 預設值 | 備註 |
| --- | --- | --- |
| 每人最多選擇品牌數 | 由 rotation 定義 | 各檔期可設定不同上限，取自 `rotations.max_selectable_auto_brand_count`（僅計入具備 active `auto` campaign 之品牌） |
| 每人每檔期可用點數上限 | 由 rotation 定義 | `rotations.max_points_per_member`，跨品牌與 campaign 合計；`0` 代表無上限 |
| 單筆交易 active-campaign 券張數上限 | 由 campaign 定義 | `max_redemptions_per_order`，僅約束既有券段之 active-campaign 舊券；`0` 代表無上限；歷史 campaign 舊券不受此限 |
| 品牌更換頻率 | 不限次數（由 frontend 管控） | 後端不做次數限制 |
| Coupon 使用順序 | FIFO（先到期先用） | 依 `expired_at`、`created_at`、`coupon_id` 排序；不符合門檻的券跳過 |
| 點數不足時 | 只換點數足夠支付的張數 | 依序發券，逐張檢查，不部分扣點 |
| 取消交易時點數 | 不返還 | 券未到期回 `available`；已到期回 `expired` |
| `consumed` 券可用性 | 不可納入下一筆交易計算 | 視同已用 |
| `coupon_valid_days` | 全域參數 | 發券時計算 `expired_at = (issued_at 所在 UTC+8 日期 + coupon_valid_days) 的 23:59:59.999`；`0` 代表當日到期 |

## 十、Rotation 輪播檔期

### 10.1 概念說明

Rotation 是樹配券 2.0 的活動檔期機制。每個 rotation 定義一段活動時間（`start_time` ～ `end_time`），並攜帶本檔期的品牌選擇上限與前端顯示參數。

用戶在某一 rotation 期間設定的品牌選擇，與該 `rotation_id` 綁定。換檔後，舊選擇自動視為失效，用戶需重新設定。

系統同一時間只應有一個 active rotation（`start_time <= now() <= end_time`，end_time 含邊界；建立時須檢查 `next.start_time > prev.end_time` 避免交界重疊）。

### 10.2 用戶品牌選擇與 Rotation 的綁定

用戶執行 `update_member_selected_brands` 時，以 `brand_ids` 作為更新後完整清單，系統計算 diff 後覆寫 `member_selected_brands`，並將當下 active rotation 的 `id` 寫入 `member_selected_brands.rotation_id`。

- 若當下無 active rotation，拒絕操作，回傳 `NO_ACTIVE_ROTATION`
- 每次執行均覆寫 `rotation_id` 為當前 active rotation 的 id

### 10.3 換檔後的 Lazy Cleanup 機制

系統不以批次清除方式處理換檔，而是在用戶進入系統時自動觸發 lazy cleanup：

**觸發點：**
- `get_member_settings`
- `update_member_selected_brands`
- `create_order`

**判斷邏輯：**
```
if member_selected_brands.rotation_id != current_active_rotation.id:
    → 視為舊檔期選擇，執行清除
```

**清除行為（同一 DB transaction）：**
1. 刪除該用戶在 `member_selected_brands` 中的所有舊檔期記錄
2. 在 `member_event_logs` 寫入一筆 `system_clear_brands` 事件：`data = {"before_brands": [被清除品牌快照], "after_brands": []}`，`created_at`：舊 rotation 的 `end_time`（語意時間點）

**冪等性：** 若已選清單已為空，skip，不重複寫入。

### 10.4 前端顯示參數

`description` 儲存於 `rotations` 表，透過 `get_current_rotation` API 供前端取得，用於顯示活動說明文字（例如「每消費 100 元可折抵 10 點」），格式為 JSON 字串 `{"order_amount": N, "point_amount": N}`，由前端自行 parse 呈現。

**重要：** `description` 目前不影響實際清算邏輯。清算時，系統依各品牌 `campaign` 的 `coupon_min_order_amount` 與 `coupon_redeem_points` 執行。

### 10.5 API 對應

| API | Rotation 相關行為 |
| --- | --- |
| `get_current_rotation` | 回傳當前 active rotation 的完整設定，及所有具備 active `auto` campaign 的品牌清單 |
| `get_member_settings` | 觸發 lazy cleanup；`max_selectable_auto_brand_count` 取自 active rotation |
| `update_member_selected_brands` | 觸發 lazy cleanup；以 `brand_ids` 全量覆寫並寫入當前 `rotation_id`；驗證品牌數上限使用 active rotation 的 `max_selectable_auto_brand_count` |
| `create_order` | 觸發 lazy cleanup；清算以 request 之 `brand_id` 為唯一品牌來源；品牌未入選（含 lazy cleanup 清空後）僅跳過新券段，舊券照常清算 |

## 十二、網路層 Timeout 因應原則

### 12.1 適用範圍

本章彙整系統中所有**同步跨系統呼叫**可能因網路層因素 timeout 的情境，並以「券、點、銀行、前端、營運、客服」六個角色定義對應做法。

以下 API 皆為唯讀查詢，或不涉及外部系統的內部讀寫，天生可安全重試，不再展開六角色因應：`get_current_rotation`、`get_member_settings`、`get_member_settings_change_logs`、`get_coupon_wallet`、`get_coupons`、`get_coupon_detail`、`get_member_orders`、`get_finalize_batch_status`、`bank_get_order`。

### 12.2 create_order → treelife-api 扣點逾時

| 角色 | 因應做法 |
| --- | --- |
| 券 | 本次新券段視為失敗，不發新券；不影響既有券段已折抵的結果 |
| 點 | 同步窗（15 秒）內不查詢確認，直接標記該筆 order「點數結果未定」，交每日 **04:00 cronjob** 對帳：確認**成功** → 因點數系統目前無法同時提供 `tree_points`/`cub_points` 細部拆分、無法據以正確發券記帳，且先前已回覆發卡主機為失敗、未發券，故呼叫**返點**（`return_point`）退點；確認**失敗** → 不處理（點數未被扣，狀態一致）；仍 **timeout** → 標記「有問題」，告警人工介入 |
| 銀行 | **不需得知**此中間狀態——`create_order` response 僅依既有券段折抵決定 `processing`/`error` 即已足夠，不額外揭露「點數結果未定」 |
| 前端 | 不涉及（此為發卡主機端 API） |
| 營運 | 僅於 cronjob 對帳仍 timeout（「有問題」）時才需人工介入 |
| 客服 | **不需得知**此中間狀態，不提供對應查詢工具 |

> **未來優化方向**（待點數系統支援同步回傳 `tree_points`/`cub_points` 拆分後啟用）：可改為同步窗內 timeout 後立即查詢確認，成功時續行發券並將點數拆分回寫，不再需要退點、也不需等待 cronjob。

### 12.3 create_order 銀行↔神坊連線層 timeout（2026-07-22 定案）

**定案做法**：銀行端**不採用**「同 `order_id` 重送」，改為非同步透過 `bank_get_order` 查詢該筆訂單實際結果，依查詢結果更新銀行內部的折抵／入帳資料，使雙方狀態一致。

| 角色 | 因應做法 |
| --- | --- |
| 券 / 點 | 不受影響，神坊仍會跑完清算，僅銀行端沒收到回應 |
| 銀行 | 連線層 timeout 後，非同步呼叫 `bank_get_order` 確認該筆訂單實際結果（`processing`/`error` 等），據以更新銀行端本地折抵資料；若查詢結果顯示此筆折抵不應存在（例如銀行端已判定該筆刷卡應取消），可透過 `batch_finalize_orders`（action=`cancel`）取消／回沖已入帳的折抵 |
| 前端 / 營運 / 客服 | 無直接影響 |

### 12.4 batch_finalize_orders 等待 ack 的連線層 timeout

| 角色 | 因應做法 |
| --- | --- |
| 券 / 點 | 不受影響，只要該 `request_id` 最終有效即會正常執行 |
| 銀行 | **冪等重送**：收到本地連線 timeout 可直接安心重送同一 `request_id`；重送若收到 `400 BATCH_REQUEST_ALREADY_EXISTS`，即視為「已受理」的確認訊號，不需額外查詢 `get_finalize_batch_status` 才能確認受理與否 |
| 前端 | 不涉及 |
| 營運 | 無需特別介入 |
| 客服 | 若核銷長期卡在非終態，查詢管道仍待後台 CRUD API（第二階段）補齊，非本次範圍 |

### 12.5 activate_member / deactivate_member → treelife 點數系統呼叫逾時

> ⚠️ 兩支 API 的成敗判定基準**不對稱**（2026-07-22 起）：`activate_member` 仍以點數系統成功為前提；`deactivate_member` 改為樹配券本地寫入成功即視為完成，點數系統呼叫改為 best-effort。分述如下。

**activate_member**（維持點數系統成功才寫入本地）：

| 角色 | 因應做法 |
| --- | --- |
| 券 | 不受影響 |
| 點 | 對 treelife 的授權操作本身具冪等性（重複呼叫不會產生副作用，已為 `TRUE` 時重複呼叫不重複寫 log），timeout 時直接重試同一操作即可，不需要類似 `create_order` 的查詢確認或每日 cronjob 對帳機制 |
| 銀行 | 不涉及 |
| 前端 | timeout 後可直接重新呼叫同一支 API，不需特殊防呆或狀態揭露 |
| 營運 | 不需新增對帳機制 |
| 客服 | 不需額外查詢工具，重試即可解決 |

> **失敗情境補充**（比照 `create_order` 的點數端失敗／我方失敗分類）：
> - **點數系統失敗**（含 timeout）：樹配券整筆失敗，本地狀態不變（`members.is_activated` 維持原值）；此操作具冪等性，前端可直接重試，安全無副作用
> - **點數系統成功、樹配券本地端寫入失敗**（`members` 更新/新增或 `member_event_logs` 寫入失敗）：屬**非預期錯誤**，回 5xx 並觸發 Sentry alert 通知工程團隊人工介入；此時點數系統端已完成啟用，但樹配券本地狀態未同步，需人工確認並補正兩邊狀態一致

**deactivate_member**（樹配券本地寫入成功即完成，點數系統呼叫為 best-effort）：

| 角色 | 因應做法 |
| --- | --- |
| 券 | 不受影響 |
| 點 | 樹配券本地寫入（`members.is_activated = FALSE` + `member_event_logs`）成功即回覆成功；`member_unauthorize` 呼叫為 best-effort，其成功與否不影響本次回應；失敗（含 timeout）觸發告警通知工程團隊另行確認並補正點數系統端狀態，不需重試、不需查詢確認機制 |
| 銀行 | 不涉及 |
| 前端 | 收到成功回應即可視為完成，不需因擔心點數系統端狀態而額外處理 |
| 營運 | 不需新增對帳機制；告警觸發後由工程團隊人工補正 |
| 客服 | 不需額外查詢工具 |

> **失敗情境補充：**
> - **樹配券本地寫入失敗**：屬非預期錯誤，回 5xx；此為唯一影響本次 API 成敗判定的情境
> - **點數系統呼叫失敗**（含 timeout）：**不影響本次 API 回應**，改觸發告警通知工程團隊，另行確認並補正點數系統端授權狀態使其與樹配券本地狀態一致

### 12.6 update_member_selected_brands 逾時後的重送建議

後端本身不限制品牌更換次數（見第九章「品牌更換頻率」），但前端會自行限制「每 N 天僅能更改一次」。若請求因網路 timeout 未收到回應，前端若直接盲目重送，可能造成：(1) 產生兩筆 `change_selected_brands` 事件；(2) 若前端「每 N 天一次」的判斷依據是讀取 `last_brand_selection_changed_at` 或異動紀錄，重複寫入可能讓前端誤判用戶已用掉本次額度，錯誤地擋下使用者原本合法的下一次操作。

| 角色 | 因應做法 |
| --- | --- |
| 券 / 點 / 銀行 | 不涉及 |
| 前端 | 呼叫 `update_member_selected_brands` 逾時未收到回應時，**先重新呼叫 `get_member_settings`（或 `get_member_settings_change_logs`）確認該筆變更是否已生效**，確認未生效才重送；不引入後端 idempotency key，靠既有唯讀 API 做「重送前先查證」 |
| 營運 / 客服 | 無需特別介入（最終狀態一致，此為前端行為建議，非後端保證） |
